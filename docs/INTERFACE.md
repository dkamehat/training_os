# インターフェイス設計書 — 人間とOSの接点

**設計原則: OSの持続性は機能の多さではなく、入力負荷と確認負荷の低さで決まる。**
M11（MVO・崩壊検知）の思想をUI層に展開したもの。全モジュールはこの負荷バジェット内でしか人間に要求できない。

---

## 1. 負荷バジェット（絶対上限）

| 接点 | 頻度 | 上限時間 | 形式 |
|---|---|---|---|
| 朝のReadiness | 毎朝 | **30秒** | タップのみ（文字入力なし） |
| ジム内のセット記録 | トレ日 | **セット間レストに吸収（追加時間ゼロ）** | 例外入力のみ |
| 週次レビュー | 日曜 | **20分** | Claudeとの1会話（コピペ不要） |
| 発信の承認 | 週1バッチ | **15分** | Yes/No/微修正のみ |
| 月次バッチ | 月1 | 30分 | 同上 |

**合計: 週あたり約1時間**。これを超える要求をするモジュールは設計不良として差し戻す。

## 2. 入力の3原則

### 原則A: 例外入力（Exception-based logging）
**「計画通り」は入力ゼロにする。** 週次生成の時点でDayページに計画セット（重量×レップ×目標RPE）が並んでいる。ジムでは:
- 計画通りに挙げた → セットの✅をタップするだけ（1タップ）
- 計画と違った → その数字だけ直す（重量 or レップ or RPE）
- メモ・違和感 → 音声入力 or 絵文字タグ（⚠️腰 / ⚠️肩 / ↔️左右差）で1タップ

これで記録時間はレスト時間に完全に吸収される。「全セットを白紙から入力する」設計は必ず崩壊する。

### 原則B: 既定値とタップ入力
朝のReadinessは4問全てをボタン化:
```
睡眠 [7h+] [6-7] [<6] [<4]   疲労 [1-3] [4-5] [6+]
痛み [なし] [違和感] [痛い]    昨日の発信 [0] [~30m] [30m+]
```
Notionデイリーログのテンプレートボタン（または朝のRoutine通知への返信）で、既定値=最頻値をプリセット。**スキップした日は「未入力」としてそのまま成立**（欠測はデフォルト扱い、罪悪感を作らない。ただし3日連続未入力はM11の縮退シグナルとして拾う）。

### 原則C: 入力は一箇所、一度だけ
同じ情報を二度打たせない。セット実績はログDBだけに入り、e1RM・遵守率・週次記事・PR表はすべてそこから**OS側が導出**する。人間は生データを一度打つだけで、加工は全部AIとルールの仕事。

## 3. 確認の3原則

### 原則D: 読むものは常に1画面
確認面は **週次ダイジェスト1枚** に集約する（P-01の出力フォーマット）:
```
🟢 今週のステータス: オントラック（685まであと67.5kg / 月次ペース+6.2kg ✅)
・S/B/D e1RM: 212 / 165 / 247（先週比 +1/+1.5/0）
・疲労: Yellow 1回（火・睡眠起因）/ 3週トレンド→横ばい
・体重: 86.2kg（7日平均、+0.15%/週 ✅）
・要判断: なし（or 1件だけ提示）
来週: 計画生成済み。Day2のBPのみ+1.25kg。
```
KPI 9個を毎週全部見せない。**逸脱したものだけ**表示し、正常項目は🟢1行に畳む。「要判断」は週に最大1件——判断を求めない週があってよい。

### 原則E: 承認はデフォルトYes
週次プログラムも発信下書きも「提案→承認」型。AIはM1のプログレッション規則どおりなら差分だけ示す（「Day2 BP +1.25kg、他は据え置き」）。規則から外れる提案をするときだけ理由を明示し、そこだけ読めばよい。全文レビューを毎週要求しない。

### 原則F: 崩壊しても責めない画面
レビューを飛ばした翌週、OSが最初に見せるのは未消化タスクの山ではなく:
```
先週はレビューなし → 前週プログラムをそのまま継続中（問題なし）。
今日やるなら20分。やらないならMVOで続行。どちらでもOS は回っています。
```
心理的負債を画面から排除する。溜まった発信下書きは自動破棄（M11）。

## 4. 接点別フロー設計

### 4.1 朝（30秒）
Routine通知（毎朝7:00）→ 4問タップ → 終了。判定はルールベース（AI呼び出しなし）。Redシグナル時のみ通知に「今日はTechnique枠 or OFF」と一行出る。

### 4.2 ジム（追加時間ゼロ）
Dayページを開く → 計画セットに✅ or 数字修正 → 違和感は絵文字タグ。第1ワーキングセットのRPEだけは必ず入れる（M3層2の当日判定に使う唯一の必須入力）。想定+1以上なら、ページ内に常設された分岐表（睡眠→セット減/痛み→種目変更/全身→トップ削除）を自分で見て縮退——**ジム内でAIを呼ばない**。

### 4.3 日曜レビュー（20分・唯一のAI対話）
Routineが日曜20:00に自発火し、Claudeが**先に**P-01を実行した状態で届く:
1. ダイジェスト1枚を読む（2分）
2. 「要判断」があれば答える（0-5分）
3. 主観を3行だけ話す（音声可: 今週どうだった/気になること/来週の都合）
4. Claudeが次週プログラム差分＋発信バッチを生成 → デフォルトYesで承認（10分）
5. ClaudeがNotion更新（現在のプログラム冒頭＋Day1-4上書き）まで実行して終了

人間がプロンプトをコピペする工程は存在しない。定型文はRoutineとprompts/に焼き込み済み。

### 4.4 発信承認（15分）
生成済みの週分（X日次4本・リールキャプション3本・note1本）を一覧で見て、各項目 Yes / 破棄 / 一行修正。動画はCapCutテンプレに流し込むだけ（テンプレ選択の意思決定ゼロ）。予約投稿ツールへ配置して終了。

### 4.5 月次（30分）
P-05バッチの結果（メタ分析差分・PR対比・自己充足率・膝壁テストのリマインド）をダイジェスト1枚で確認。DOI検証が必要なclaims追記だけ個別承認。

## 5. インターフェイスのKPI（インターフェイス自体も計測・改善対象）

| 指標 | 取り方 | 閾値 |
|---|---|---|
| Readiness入力率 | 入力日÷全日（週） | <60%でフォーム簡素化を検討 |
| セット記録の即時性 | 当日入力か後日まとめ打ちか | まとめ打ち常態化=例外入力が機能していないサイン |
| 週次レビュー所要時間 | 実測 | 20分超過が2週続いたらダイジェストを削る |
| 発信承認の破棄率 | 破棄÷生成 | >40%なら生成品質側を直す（人間の負荷で吸収しない） |

月次レビューでこの表を見て、**インターフェイスの摩擦を下げる変更を毎月1つだけ**入れる（一度に変えない）。

| 部品 | 実装 |
|---|---|
| 朝の4問 | Notionデイリーログのテンプレートボタン＋Routine通知（7:00） |

| 絵文字タグ | ログDBのマルチセレクト（⚠️腰/⚠️肩/↔️左右差/💤/😤） |

| 崩壊検知 | Routineが未実行を検知し「責めない画面」文面で再通知 |
